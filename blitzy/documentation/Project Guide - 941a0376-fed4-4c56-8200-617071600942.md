The audience is the service's existing loopback consumers, and the impact is a second greeting surface with the address, startup line and existing response unchanged. **A held port reads as a healthy start.** Express registers the `app.listen` callback as the socket's error handler, so `EADDRINUSE` is consumed: the process prints `Server running at http://127.0.0.1:3000/`, writes nothing to stderr and exits 0 without listening (`server.js:11-13`). The raw `http` handler this replaced failed loudly, with exit 1 and a stack trace. Any supervisor, unit file or container restart policy keyed on exit status or on the startup line therefore treats the failure as a healthy start, and a readiness check that greps the log line proves nothing. The remedy is an error listener with a non-zero exit, which the request's no-error-handler and smallest-diff constraints excluded. Decide whether that constraint still binds the deployment.

**No automated guard on a byte-exact contract.** The contract is precise: status 200, a header value with no charset parameter, and bodies of 14 and 13 bytes. Because the specification forbade a test suite and a `scripts` block, nothing in the repository fails if `server.js:8-9` is edited to `res.send(...)`, which emits `text/html; charset=utf-8` when no type is preset and appends `; charset=utf-8` to a preset `text/plain`. The one demonstration that the delivered form is correct is behavioural: the header stays parameter-free under `Accept: text/html` and `Accept: application/json`. Adding the suite (Section 2.2, 3.0 h) is the decision that closes this.

**Install resolution is not reproducible.** `express` is declared at `^5` with no lockfile, and both follow from the request rather than from oversight. A clean install resolved `express@5.3.0` across 65 packages and wrote no lockfile; `npm ci` fails with EUSAGE and `npm audit` with ENOLOCK, so the customary reproducible-install and advisory gates are unavailable. The framework defaults the service depends on — 404 page shape, case-insensitive and trailing-slash path matching, chunked framing — are properties of the resolved Express release, so a future 5.x can change observable behaviour with no diff here. Pinning the range and committing a lockfile (1.0 h) restores both gates.

**The tracked project notes no longer describe the tree.** `blitzy/documentation/Project Guide.md` still asserts a manifest-free, zero-install repository, a byte-identical 14-line `server.js`, three tracked paths, and a second start exiting 1 with a stack trace. The tree now holds a three-field manifest, a modified 13-line `server.js`, four tracked source paths plus one document, and a second start that exits 0 silently. The request forbade touching documentation, so the drift is a consequence of delivery rather than a defect in it. A documentation-only refresh (1.0 h) closes it; until then the file should not be used as a statement of the tree.

**The manifest has no runtime floor and no publication guard.** Because `package.json` may hold only `name`, `version` and `dependencies`, there is no `engines` field and no `private: true`. Express 5 declares `node >= 18`, and every measurement here was taken on Node 22.23.5, so the floor is satisfied on this host but is neither declared nor enforced: an install on an older runtime would fail at startup with nothing in the manifest explaining why. Likewise, nothing marks the package as unpublished. Adding `engines` and `private` (folded into the deployment task, 2.5 h) makes the supported runtime explicit once the field limit is relaxed.

# 9. Development Guide

**System prerequisites**

- Node.js 22.x — every command below was run on `v22.23.5`. Express 5 declares `engines: {"node": ">= 18"}`, and the manifest carries no floor of its own, so the runtime must be checked on the host.
- npm 11.21.0 (any npm 9+ satisfies the install commands).
- A POSIX shell, `curl` and `od` for verification. `ss`, `lsof`, `nc` and `xxd` may be absent; the listener check below reads the kernel socket table instead.
- No database, cache, queue, broker or external endpoint. No credentials, secrets or environment variables of any kind.
- TCP port 3000 on 127.0.0.1 free. The host and port are literals in `server.js` (`:3-4`), so the service cannot be moved by configuration.

**Environment setup**

There is nothing to configure. The service reads no environment variable, no `.env` file and no configuration file; `hostname` and `port` are constants. Confirm that with `grep -n process.env server.js` (no match). All commands run from the repository root.

**Troubleshooting**

| Symptom | Cause | Resolution |
|---|---|---|
| `Error: Cannot find module 'express'` and exit 1 | Dependencies not installed in this clone — the manifest declares Express, it does not vendor it | Run the install command; confirm with `npm ls --depth=0` |
| A second `node server.js` prints the success line, writes nothing to stderr and exits 0 | The port is already held. Express registers the `app.listen` callback as the socket's error handler, so `EADDRINUSE` is consumed | Probe the port first (`000` means free); find the pid that owns the socket and stop that pid — never match a process by name |
| `npm error code EUSAGE` from `npm ci` | `npm ci` requires a lockfile, and no lockfile may exist here | Use `npm install --no-package-lock --no-audit --no-fund` |
| `npm error code ENOLOCK` from `npm audit` | Advisory checks require a lockfile | Expected under the current policy; the advisory gate returns with the lockfile work in Section 2.2 |
| `Content-Type: text/html; charset=utf-8`, or `text/plain; charset=utf-8`, on a contract route | A handler was changed to `res.send(...)`, which sets a type and appends a charset | Restore `res.writeHead(200, { 'Content-Type': 'text/plain' }).end(<literal>)` |
| Startup fails on an older runtime | Express 5 requires Node ≥ 18 and the manifest declares no floor | Use Node 22.x |
| `//`, `/GOOD-EVENING` or `/good-evening/` answer 200 | Framework-default path matching (case-insensitive, one optional trailing slash) | Expected; only the framework 404 handler and a custom route would change it |
| `git status` shows `node_modules/` | It is an untracked install artifact; no `.gitignore` exists | Leave it untracked and stage by explicit path |

## G. Glossary

| Term | Meaning in this guide |
|---|---|
| AAP | The technical specification this change was delivered and assessed against. Its requirement set (R1–R4, plus the derived constraints) and its out-of-scope list are the yardstick for every completion and compliance statement here. |
| R1–R4 | The four requested changes: confine application-code change to `server.js`; add `express` as the sole new dependency; add `GET /good-evening`; preserve the `GET /` response. |
| Catch-all | The retired `http.createServer` handler that answered every path and method with `200 Hello, World!`. Removing it is what makes path-based routing possible. |
| CommonJS | The module system the entry point uses. It holds because `package.json` carries no `type` key; a `"type": "module"` value would break `require` at line 1. |
| Emission form | `res.writeHead(200, { 'Content-Type': 'text/plain' }).end(<literal>)` — the one form, used on both routes, that writes the header verbatim and the body byte-exact. `res.send(...)` is not equivalent: it sets a type and appends a charset. |
| Framework default | Express's own behaviour for any input the contract does not specify — 404 for unknown paths and methods, `Allow: GET, HEAD` for `OPTIONS`, case-insensitive matching with one optional trailing slash. |
| Loopback | The address `127.0.0.1`. The service binds it only, so it is unreachable from any routable address; this is the sole exposure control in place. |
| Manifest | `package.json`. Here it holds exactly `name`, `version` and `dependencies.express` at `^5`. |
| Parameter-free content type | `Content-Type: text/plain` with no `; charset=...` suffix, as the contract requires and as every contract response was measured. |
| Path-to-production | The work still needed to operate the delivered service safely: tests, startup failure reporting, reproducible installs, deployment supervision, documentation and hardening. |
| Byte-exact | Matching the contracted bytes exactly — 14 for `Hello, World!\n`, 13 for `Good evening\n`, each with a single trailing newline. |
