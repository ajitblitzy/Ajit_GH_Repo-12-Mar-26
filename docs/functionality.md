# Functionality Reference

The service comprises three functionalities — **F-001 HTTP Server Listener**, **F-002 Uniform Request Handler**, and **F-003 Startup Readiness Logger** — implemented entirely in the single-file Node.js service `server.js`, which uses only the standard-library `http` module (`Source: server.js:L1-L14`). This reference is written for a technical audience. Statements about the application's behavior cite the exact `server.js` line(s) they reflect; a few runtime details — the response headers generated by Node's `http` module and the error output observed on a failed bind — are attributed to Node.js `http`-module semantics or to scoped runtime observations rather than to a source line.

## F-001 — HTTP Server Listener

F-001 binds a TCP listener on host `127.0.0.1` (`Source: server.js:L3`) and port `3000` (`Source: server.js:L4`) via `server.listen(port, hostname, callback)` (`Source: server.js:L12`). The server object being bound is created by `http.createServer(...)` (`Source: server.js:L6`).

- **Bind target.** Host `127.0.0.1` (`Source: server.js:L3`) and port `3000` (`Source: server.js:L4`).
- **Bind call.** `server.listen(port, hostname, callback)` (`Source: server.js:L12`).
- **Server object.** Created by `http.createServer(...)` (`Source: server.js:L6`).
- **Lifecycle / bind semantics.** The `listen` callback fires exactly once, after the socket is successfully bound (`Source: server.js:L12-L14`). This one-time startup path is diagrammed as workflow **W-1** in [`./architecture.md`](./architecture.md).

**Example (run + log):**

```sh
node server.js
```

```text
Server running at http://127.0.0.1:3000/
```

The stdout line is written only after the bind succeeds (`Source: server.js:L12-L14`); its content is documented under F-003 below.

## F-002 — Uniform Request Handler (KEY functionality)

**This is the KEY functionality.** It defines the entire observable HTTP behavior of the service.

For **every** request it receives, the handler runs the same three statements:

- sets the status code to `200` (`Source: server.js:L7`);
- sets the response header `Content-Type: text/plain` (`Source: server.js:L8`); and
- ends the response with the body `Hello, World!\n` — the 13 ASCII characters `Hello, World!` followed by a single line-feed byte (`\n`, `0x0A`), 14 bytes total; the trailing `\n` is one newline byte, not the two literal characters `\` and `n` (`Source: server.js:L9`).

The `req` object is **never inspected** — no request method, path, query string, headers, or body is read anywhere in the handler — so the service presents a single catch-all with no routing and no path- or method-based dispatch (`Source: server.js:L6-L10`). This per-request path is diagrammed as workflow **W-2** in [`./architecture.md`](./architecture.md), and the complete response contract (including the headers added automatically by the `http` module) is documented in [`./api-reference.md`](./api-reference.md).

**Example (`curl`):**

```sh
curl -i http://127.0.0.1:3000/
```

```text
HTTP/1.1 200 OK
Content-Type: text/plain
...
Hello, World!
```

In the output above, the `...` stands in for the response headers generated by Node's `http` module (`Date`, `Connection`, `Keep-Alive`, and `Content-Length: 14`), which are documented in [`./api-reference.md`](./api-reference.md). The body is `Hello, World!` followed by a single trailing line-feed byte (`\n`, `0x0A`) — 14 bytes total (`Source: server.js:L9`); that terminal newline is why the printed output breaks the line after `Hello, World!`.

Because `req` is ignored (`Source: server.js:L6-L10`), the handler runs the same application logic for every request that reaches it, regardless of method or path — for example, `curl -X POST http://127.0.0.1:3000/anything` yields the same `200` status, `Content-Type`, and body as `GET /`. This uniformity is a property of the application code; around it, Node's `http` module applies protocol-level behaviors (notably `HEAD`, whose response carries no body; `CONNECT`, which is not delivered to this handler; and unrecognized method tokens such as `FOOBAR` or a lowercased method, which Node rejects with `400 Bad Request` before the handler runs). The complete method-and-protocol contract is documented in [`./api-reference.md`](./api-reference.md).

## F-003 — Startup Readiness Logger

After a successful bind, a single line is written to standard output from within the `listen` callback: `Server running at http://127.0.0.1:3000/` (`Source: server.js:L13`, emitted inside the `server.listen(...)` callback `Source: server.js:L12-L14`). This is the sole explicit application readiness log in the complete source (complete-source inspection, `Source: server.js:L1-L14`); Node.js, the process, and the operating system may still emit their own signals independently of the application code.

**Example (expected stdout):**

```text
Server running at http://127.0.0.1:3000/
```

## Configuration constants (C-1)

Configuration is defined as hard-coded module-scope literals in the source (`Source: server.js:L3-L4`); inspection of the complete source shows **no** environment-variable or config-file override mechanism (constraint **C-1**, complete-source inspection `Source: server.js:L1-L14`). The two constants are:

| Constant | Value | Source | Overridable? |
|----------|-------|--------|--------------|
| `hostname` | `127.0.0.1` | `server.js:L3` | No — hard-coded module-scope literal (C-1) |
| `port` | `3000` | `server.js:L4` | No — hard-coded module-scope literal (C-1) |

Changing the host or port therefore requires editing `server.js` directly (`Source: server.js:L3-L4`).

## Operational limitations

- **A-2 — Loopback-only reachability.** The server binds the loopback address `127.0.0.1` (`Source: server.js:L3`), so it is reachable only from the local host; it is not exposed on external or other non-loopback network interfaces (`Source: server.js:L3`).
- **C-2 — Unhandled bind failure.** The source attaches no `error` listener to the server or to the `listen` call (complete-source inspection, `Source: server.js:L1-L14`). Under Node.js's unhandled-`error` semantics, a bind failure — for example, when port `3000` is already in use — therefore surfaces as an uncaught exception that terminates the process; this crash behavior is an inference from the absent listener plus Node's `error`-event handling, not a value written in the source. As a scoped runtime observation (Node.js v22.23.1, Windows), starting a second instance on the same host and port failed with `Error: listen EADDRINUSE: address already in use 127.0.0.1:3000` and the process exited with code `1`; the exact message text and exit code are environment- and version-dependent and are not a guaranteed cross-version contract.
- **C-3 — Single-log observability.** The one stdout readiness line (`Source: server.js:L13`) is the **only explicit application log statement in the complete source**; the application performs no logging of requests, errors, or metrics (complete-source inspection, `Source: server.js:L1-L14`). This does not mean no other signals exist — Node.js and the runtime can still emit output independently of the application, such as the stderr stack trace on the unhandled bind failure described in **C-2**.
